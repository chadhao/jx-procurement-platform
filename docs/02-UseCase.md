## 4. 用例详述

> ★ **转向 ③ 统一改造口径（V1.3，适用于 UC-02~11、UC-15~17 等"审批类"用例）** —— 下列**共同变化**不再在每个用例内逐条重复；各用例内的"③ 改造"格只写**该用例特有**的差异。
> ① **发起入口**：由"飞书原生审批页"改为 **我方表单页**（在飞书内以 `SIDEBAR` 打开，`01a §5.1 / §5.3`）；
> ② **审批动作**：审批人在飞书点「**同意 / 拒绝**」（→ 快捷回调），或在我方页面点同两键（`01a §5.2`）；**转交 / 加签 / 回退 / 撤回只有我方页面有入口**（飞书侧无按钮）；
> ③ **单据编号**：由**我方生成**（`{前缀}-{YYMM}-{####}`，`01a §3`），**不再由飞书流水号控件产生**；
> ④ **事件来源**：由"订阅飞书 `approval_instance` 事件"改为「**快捷回调 + 我方主动推送（`external_instances`）+ 每 5 分钟对账**」（`01a §6 / §7.2`）；
> ⑤ **真相源**：审批状态 / 逐审批人轨迹**以我方库（`t_flow_op_log`）为准**（`01a §6.2`）；飞书侧只作展示 / 待办 / 通知；
> ⑥ **可用性**：回调「**落盘即 200、业务异步**」；**服务整体不可用归"高可用"**、**不做线下兜底**（`01a §7.2 D2`）。
> ⑦ **通知触达**（V1.5 新增）：★ **推三方实例（`external_instances`）只让任务进「待办」，不发任何通知** —— **通知须我方另调** `POST /open-apis/approval/v1/message/send`（`template_id=1008`「收到审批待办」）；**「待办进列表」与「发消息通知」是两个独立动作**（UC-30）。
> ⑧ **回调报文**（V1.5 新增）：★ **按官方字段名解析**（`action_type` / **`user_id`** / **`approval_code`** / `instance_id` / `task_id` / `token` / `message_id` …）—— ★ **官方不发顶层 `biz_no`**，`biz_no` **只能靠 `action_context` 携带 JSON 回传**（推实例时写入 `task_list[].action_context`）；★ `user_id` 与 `open_id` **双读兼容**（UC-21 / UC-20）。

### UC-01　飞书免登与身份识别

| 项 | 内容 |
|---|---|
| **参与者** | 全角色（主）、自建系统 |
| **前置条件** | 飞书自建应用已创建并申请「通讯录读取（免登用）」权限；用户为飞书组织成员 |
| **主流程** | 1. 用户访问自建系统受保护页面。<br>2. 系统检测到无有效会话 → 跳转飞书免登授权。<br>3. 用户完成授权，回调 `GET /auth/feishu/callback`。<br>4. 系统用授权码换取用户身份，得到 `open_id`。<br>5. 系统按 `t_user_role` 查 `open_id → 角色`。<br>6. 系统建立会话，按角色加载可见行范围与可见列集合。<br>7. 用户进入页面。 |
| **异常流 / 备选流** | A1. 回调失败 / 授权被拒 → 提示失败，回到未登录态，不建立会话。<br>A2. `open_id` 未映射到任何角色 → **拒绝进入业务页面**（默认无权限），仅显示提示；由系统管理员补配角色。<br>A3. 用户在飞书被调岗 / 角色变更 → 下次请求时重新解析角色，权限**即时生效**。 |
| **后置条件** | 会话建立；系统已知「你是谁」；行 / 列权限可按角色生效 |
| **关联需求** | FR-M0-10、FR-M5-04 |

> ★ 行·列权限的前提是「知道你是谁」——飞书免登是本系统分权能力的前置。

> ★ **③ 改造（V1.3）**：免登后进入的业务页面须**适配 `SIDEBAR`（飞书侧边抽屉）**打开——现 `web/src/styles.css` **全文无 `@media`** ＋ sidebar 固定 216px → **抽屉内布局会崩**（`audit-frontend-docs` 第 49 阶段命中）→ 前端须补**响应式外壳**（`01a §5.1`）。★ **入站回调 / 内部端点不走免登**（飞书请求无 cookie，须绕开 `requireSession`，见 UC-21 / `01a §6.4`）。**本用例其余不变（保留）。**

### UC-02　采购报备与备付金签领（采一档 <1,000 元）

| 项 | 内容 |
|---|---|
| **参与者** | 申请人（主）、综合运营主管、飞书审批引擎、自建系统 |
| **前置条件** | 采购报备单模板已建好并订阅；备付金实有金额已知（不设定额） |
| **主流程** | 1. 申请人在**我方表单页**（飞书内 `SIDEBAR` 打开）提交采购报备单（填分类、二级明细、数量、金额、供应商、事由、到货日期）。<br>2. 我方校验通过 → **生成单号**（`BA-YYMM-####`，`01a §3`）并**推送三方实例**到飞书（`external_instances`）；申请人确认已发起。<br>3. 审批人在**飞书点「同意 / 拒绝」**（→ 快捷回调）；我方状态机**异步推进**、落 `t_flow_op_log`（真相源）。<br>4. 综合运营主管在飞书内审批「备付金是否充足」（只判付款能力，不判需求必要性）。<br>5. 校验防拆分与次数上限（**不通过即转档或退回，须在拨付款项之前完成**）：系统以台账红标提示（同供应商 + 同二级明细当月累计 ≥1,000 元即预警并强制转采二档）。<br>6. 综合运营主管拨付备付金，**申请人在备案单上签领**（签领人 / 金额 / 日期）。<br>7. 自建系统登记**备付金签领记录**（FR-M1-01）。<br>8. **申请人自购**（谁申请谁购买；本档明文豁免「禁止自我经办」）。<br>9. 申请人回交付款凭据；自建系统补录审批人、付款凭据号（FR-M1-03）。<br>10. 到货后由申请部门或仓储完成到货登记与入库。<br>11. 综合运营主管按月凭单据向集团核销补足，登记核销后余额；台账与月度报送引用。 |
| **异常流 / 备选流** | A1. 备付金不足 → 综合运营主管在**三项处置中择一**：① 现场向集团申请备付金　② 延后申请、延后执行　③ 拒绝审批；三项处置须在单据上留痕。<br>A2. 拆分 / 次数校验不通过 → 转采二档或退回，不拨付。<br>A3. 综合运营主管本人需求（即使 <1,000 元）→ **审批上抬至主管领导**，本人不得自审自购，台账单独标记。<br>A4. 综合运营主管不在岗 → **备付金审批不得代理**；采一档顺延或改走延后执行；确需即时的走紧急采购通道。 |
| **后置条件** | 签领记录、付款凭据与备案单逐笔一一对应；核销后余额可查 |
| **关联需求** | FR-M1-01、FR-M1-03、FR-M1-05、FR-M1-07、FR-M2-04、FR-M4-04、FR-M4-05 |

> ★ 本档是**三道门槛（签不签合同 / 走不走公户 / 走不走合同两级审批）的唯一豁免档**，故防拆分规则是本档能否成立的前提（制度第十八条、第二十一条）。

> ★ **③ 改造（V1.3）**：发起 / 编号 / 事件来源按 §4「统一改造口径」①③④替换（原"飞书内提交 + `approval_instance` 事件 + 解析归档单号"**作废**）；**审批人仍可在飞书点同意 / 拒绝**（走回调）。本档**无转交 / 加签 / 回退**需求（采一档仅备付金审批），但**发起人可撤回**（UC-25）。
