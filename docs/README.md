## 关键定案（易错点，勿再反复）

| # | 定案 | 依据 |
|---|---|---|
| 1 | **幂等键 = 事件级唯一 ID**（2.0 版 `header.event_id` / 1.0 版 `uuid`）；**不是** `instance_code + status` | 飞书《事件概述》官方原文；`instance_code + status` 会吞掉驳回重提的第二次 PENDING |
| 2 | 幂等保留窗口 **≥ 7.1 小时**（重试 15 秒 / 5 分钟 / 1 小时 / 6 小时，最多 4 次） | 飞书《事件概述》 |
| 3 | **必须先按 `approval_code` 调「订阅审批事件」接口**，否则一条事件都不推 | 飞书审批事件文档「前提条件」 |
| 4 | **单实例**部署（长连接集群模式不广播）；**同步路径绝不阻塞**（有序事件会阻塞后续） | 飞书《事件概述》 |
| 5 | **单号由飞书「流水号控件」生成**，自建侧只读、不设编号器 | 飞书帮助中心《管理员使用流水号控件》 |
| 6 | **PO 不作独立单据**，沿用合同 / 简式订单（CT）号 | 工具表·单据清单（11 张不含 PO）＋ 批复 D8 |
| 7 | 11 张审批模板**人工在审批后台建**（API 不支持条件分支） | 飞书开放平台《创建审批定义》 |
| 8 | **行·列权限口径已定案（2026-09-26）**：采纳 PRD §4.2；行级只用 **6 令牌 + `DENY`，不引入条件表达式**；新增**「系统管理」后台页**（`/admin`，仅系统管理员）自助配置 | 用户裁决 2026-09-26；PRD FR-M5-09~11 / §5.6 / API §3.9 |
| 9 | **`Idempotency-Key` 语义 = 三分支**：同键 + 同载荷 → **200 复用首次结果**（附 `idempotent_replay:true`）；同键 + 异载荷 → **40900**；未带键 → 无幂等保护。★ 载荷指纹是「规范化业务字段的 SHA-256」，**关联项顺序不敏感**、「未传金额」≠「传 0」 | 原 `05-API.md` §2.2/§8 与 §3.5 措辞**自相矛盾**（B15），按语义优先裁定并同步四处；实现见 `internal/submission/idem.go`、TC-36/37 |
| 10 | **`api:petty-cash` / `api:submission` 不进行·列权限矩阵**，只由处理器 `authorizeRole` 硬校验角色 | 若同时入矩阵会出现「矩阵可配、处理器更严」的**假配置**（改矩阵不生效，误导运维）；待资源枚举入库后统一迁移 |
| 11 | **`POST /api/submission` 的 `biz_no` 必填**（缺失 → 40000）。★ 它是业务唯一键 + 幂等去重锚点；**SQLite 列级 `UNIQUE` 对 NULL 不生效**，允许为空则重复登记无解 | 飞书无此约束，属实现层必须自建；迁移 `0002` 另加 `COALESCE(biz_no,'')` 表达式唯一索引作硬兜底（B20） |
| 12 | **幂等键按调用方隔离**：唯一索引 `(target_id, actor_open_id)`；`FindIdem` 必须带 `actor` | 否则甲方登记的键被乙方复用时会读到**甲方的报送记录**（信息泄漏）（P2-8） |
| 13 | **`t_submission` 行级权限为过渡降级**：无部门/申请人列，`DEPT`/`CHARGE_DEPT`/`ASSIGNED`/`PARTICIPATED` 统一按 `created_by = me`，未知/`DENY`/空身份 → `1=0` | 保守收紧（宁可少不可多），**绝不越权**；待 Q14 台账字段口径定稿后按真实列重建（B21） |
| 14 | **集团报销跟踪（`/api/reimbursement`）与报送（`/api/submission`）不合并**：前者＝报销类事前申请的审批外跟踪，后者＝湖南侧流程完成后的对外报送 | 二者业务对象与判定规则不同（报送有「无凭证视为未提交」，报销没有）；合并会互相污染（docs/06 §I-1） |
| 15 | **变更链按合同号匹配一律用「键名无关的精确值比较」，绝不使用 `LIKE`**：`json_each(ext_json)` 展开对象后对任意键的值做等值比较，`json_valid` 守卫脏行 | `LIKE '%ou_ab%'` 会命中 `ou_abc`（前缀越权，§H.10 P0-A）；写死 `$.contract_no` 又会在 Q14 定稿后失效（docs/06 §I-2） |
| 16 | **年度归档（`scripts/archive-year.sh`）只导出、不删除在线数据**；在线库瘦身须独立批准后另行执行 | PRD FR-M4-08 验收标准「**归档后历史仍可查**」（docs/06 §I-4） |
| 17 | **台账类型键（`L01..L12`）以单文件 `web/src/ledgerTypes.js` 为唯一出处**，不得再在前端自造键 | 曾因前端写 `purchase`/`expense`/`petty_cash` 而后端为 `L01..L12`，导致台账列表**恒空**（FR-M4-01 / docs/06 §I-5） |
| 18 | **`field_id → biz_field` 映射的结果必须真正被消费**：抽取到 `t_instance` 规范列（金额/供应商/用途/部门/单号），非规范列字段汇入台账 `ext_json` | 原实现只把映射写进 `t_instance_field`，`amount_cents`/`supplier`/`purpose_class_*` **恒为空且不报错** → 看板金额、防拆分「同供应商当月累计」（D7）、800–1,000 元抽查清单**全部静默失效**（FR-M2-08 / docs/06 §J.2 **P0-C**） |
| 19 | **`ext_json` 必须携带已映射字段**（文本存为 JSON 字符串，保证 `json_each(...).value = '<合同号>'` 等值命中） | 原实现写死 `"{}"` → 变更链按合同号检索**恒为 0 且不报错**（FR-M2-08/FR-M4-07 / docs/06 §J.2 **P0-D**） |
| 20 | **`doc_type → ledger_type` 只能指向「实例级」台账**（`L01–L07` + `L09`）；`L08`（手工主数据）/`L10`（只读汇总）/`L11`（派生，数据源＝CT+GR）/`L12`（本期不启用）**禁止指向**，导入层硬拦 | 写入模型是「一实例一行」，指向汇总表会**逐单插行使台账数字翻倍**（架构 §3.4 / docs/06 §J-3） |
| 21 | **配置映射导入必须拒绝未替换的占位符**（`REPLACE_ME`/`替换`/`TODO:`/`<待填>`），且**任一条不合规即整体拒绝、不做部分导入** | 样例被原样导入 = 写入一批指向**不存在** `approval_code` 的映射 → 模板永远订阅不到事件、系统无数据、**无任何错误日志**（docs/06 §J-1） |
| 22 | **抽取匹配只用 `field_id → biz_field` 精确匹配，绝不按控件中文名模糊猜**；接口权威值（`serial_number`/`open_id`）**不被表单值覆盖**（只填空） | 模板改名极常见，按中文名匹配会在改名后**静默抽错列**（docs/06 §J-5 / §J-6） |
| 23 | **`PC`（采购变更单）与 `SS`（单一来源理由书）同落 `L09` 例外事项台账**；`RFQ`/`BJ`/`QC` **不落账**（未配置 → 不写台账，是设计意图） | 采购变更属「**例外流程三条**」（采购变更/独家采购/紧急采购）；`RFQ`/`BJ`/`QC` 不构成独立台账（docs/06 §J-7 / §J-8） |
| 24 | **新增配置键必须同时有消费端**：阈值只登记代码真正读的（`split_supplier_month`/`spot_check_range`）；`purchase_tier`/`emergency_hours`/`submit_workdays` 当前**无消费端** → 导入时提示「**假配置**」；`enum.*` **故意不纳入导入** | 把「配了、没人读」做成可配项，就是重现 §J.2 **P0-C** 的同类缺陷（同一类问题见决策 #10）（docs/06 §J-9） |
| 25 | **文档宣称「由配置决定」时，必须同时存在「写入通道」与「消费端」**，否则须在文档中标「文档约定、尚未实现」 | `t_ledger_field_def` 被文档写作「决定 `ops` 键名」，实际 `UpsertLedgerFieldDef` / `ListLedgerFieldDefs` **均零调用者**（仅 `is_sensitive` 被读）→ 已改用 `/api/ledger` 只按 `writable_fields` 白名单校验的实情表述（**B27**，docs/06 §J.5） |
| 26 | **`PATCH /api/ledger/{table}/{id}` 只校验 `writable_fields` 白名单，不校验台账字段定义**；`writable_fields` 为空 → 该台账整体只读（**40901**） | 字段名口径属**约定**而非系统约束；`ops` 键名不受约束（B27）。故「运营表可写字段与责任人」是**纯配置**，而「字段清单本身」要配置驱动须先补写入端口（属编码） |
| 27 | ★ **Q14 已闭合（2026-09-26）**：配置侧＝`t_permission_rule.writable_fields`（空＝只读）；编码侧六项已实施——`L07` GR+QC **各写一行 + 查询侧关联**、`L11` **派生视图不落行**、变更链键名**收敛为 `contract_no`/`related_biz_no`**、`t_ledger_field_def` **补写入端口并作为写接口白名单**、报送行级权限**按真实列重建**、看板**标量键同投影** | 用户对《Q14 待确认清单》表态「全部按你的建议执行」；详见 docs/06 §K |
| 28 | **键名是契约**：`ext_json` 里的跨单据关联键**只认** `contract_no`（合同链）与 `related_biz_no`（其他上下游）。**不得再做「任意键名等值匹配」** | 旧实现用 `json_each` 扫任意键，会把**恰好等于合同号的无关值**也拉进来（如某行把 `original_biz_no` 填成合同号）。收敛后键名写错即查不到——这是**要的**（TС-46 固化） |
| 29 | **跨单据关联查询必须同样施加行级过滤** | 漏掉会把**别部门**的检验结论挂到本部门行上——越权发生在「看起来只是多显示了一个字段」的地方（docs/06 §K.2 **P1-C**） |
| 30 | **列投影递归：`deny` 与敏感列在任意层级生效；`column_allow` 只在顶层生效** | 前者防「嵌套块里的金额原样泄漏」（B19 / §K.2 P1-A）；后者防「递归套用 allow 把嵌套块结构键一并删掉 → 丢合法数据」（§K.2 P1-B）。扁平行上必须与旧 `Project` 行为完全一致 |

| 33 | **`biz_date` 全系统唯一格式 `YYYY-MM-DD`**，月份键统一由 `monthKey()` 归一为 `YYYY-MM` | 原实现三种格式并存：存储 `YYMM`、`formulaFlags` 去连字符截 4 位得 `"2026"`（**整年**）、看板要 `YYYY-MM`；且 `Ingest` **从不写入** `biz_date` → 「同供应商当月累计」实际按**整年**统计（指标本身是错的）（docs/06 §K.9 **B32**） |
| 34 | **`PassthroughBizFields` 只登记「有明确去向」的键**；无消费端的键**移除** | 否则诱导填表人以为"填了就生效"；`original_biz_no` 曾被登记但代码从不读它（docs/06 §K.9 **B33**） |
