## 3. ★★ 未闭合问题（按阻塞度排序）

### 3.1 `R33`【最高阻塞】服务器 `/etc/resolv.conf` 被 `dhcpcd` 周期性写空 ⇒ DNS 间歇失效

**现象**：审批对账**每 5 分钟一拍**，频繁报：

```
feishu: 调用 /open-apis/approval/v4/external_instances/check 失败:
  Post "https://open.feishu.cn/…": dial tcp:
  lookup open.feishu.cn on [::1]:53: read udp [::1]:…->[::1]:53: read: connection refused
```

**证据链（完整、可复现）**：

| 项 | 实测值 |
|---|---|
| `resolv.conf` 状态 A（正常） | `size=166` · `nameserver` 行数 **1**（`nameserver 192.168.10.1`）· `md5=dc5c4d9f` |
| `resolv.conf` 状态 B（**坏**） | `size=114` · `nameserver` 行数 **0** · `md5=b43fb671` |
| 状态 B 的**实际内容** | `# Generated by dhcpcd` ＋ 两行 `.head`/`.tail` 提示注释 —— **没有任何 `nameserver`** |
| 翻转频率 | **约每 15 秒 ~ 2 分钟一次**（采样实测：`17:13:35` 坏 → `17:14:10` 好 → `17:14:27` 坏 → `17:14:42` 好 → `17:14:58` 坏 → `17:15:16` 好 → `17:15:27` 坏 → `17:15:43` 好 → `17:17:01` 坏 → `17:17:16` 好 ……） |
| 写入者 | **`dhcpcd` PID 660**（`dhcpcd: enp1s0 [ip4] [ip6]`，自 **6 月 27 日**运行至今）；★ 而 `systemctl is-active dhcpcd` = **inactive** ⇒ 它是**遗留的独立进程**，不受 systemd 管理 |
| 并发网络管理 | `/etc/network/interfaces` 含 **`iface enp1s0 inet dhcp`**，且 **`networking.service` = active** ⇒ **ifupdown 与 dhcpcd 同时在管同一块网卡** |
| 坏状态文件头差异 | 坏版头为 `# Generated by dhcpcd`（**通用**），好版为 `# Generated by dhcpcd from enp1s0.dhcp`（**接口专属**）⇒ 二者来自 **dhcpcd 的不同写入路径**（疑与 `[ip6]` 的 RA / DHCPv6 事件触发重写有关，**此点未最终确证**） |

**根因（已确证的部分）**：`dhcpcd` 反复重写 `/etc/resolv.conf`，其中一部分写入路径产生**不含任何 `nameserver` 的版本**；而 **Go 的 `net` 解析器在配置里找不到 `nameserver` 时会回退到内置默认服务器 `127.0.0.1:53` 与 `[::1]:53`** —— 报错里的 **`[::1]:53` 正是该默认列表的最后一项**（本地无 DNS 服务监听 ⇒ `connection refused`）。
★ **判据**：报错主机是 `[::1]`（而不是 `192.168.10.1`），即**只可能**来自 Go 的内置默认，故可反推"当时读到的配置里没有 `nameserver`"。

**影响面（不止对账）**：

| 受影响能力 | 实测 |
|---|---|
| 飞书**长连接** | ★★ `Post "https://open.feishu.cn/callback/ws/endpoint"` 同样报该 DNS 错误；**累计断开 23 次** ⇒ 事件接收通道**时断时续** |
| 审批**对账** | **累计失败 25 次**（每 5 分钟一拍，落在坏窗口即失败） |
| 组织同步**事件回源** `contact/v3` | 同受影响的出方向调用（间歇失败 ⇒ `field_gaps` / 回退事件体字段） |
| 组织同步**全量拉取** | 同上（本次全量曾成功，属"恰好落在好窗口"） |
| Bot **通知推送** / **卡片刷新** | 同上 |
| **免登 token 交换**（`authen/v2/oauth/token`） | 同上 ⇒ 用户可能偶发登录失败 |

**建议修法（★ 系统级变更，须在服务器上执行）** —— 二选一，**推荐方案 A**：

```bash
# ── 方案 A（推荐，最小侵入）：让 dhcpcd 不再管理 DNS，改为静态配置 ──
#   1) 让 dhcpcd 不再 hook resolv.conf
echo "nohook resolv.conf" | sudo tee -a /etc/dhcpcd.conf
#   2) 静态写死（主 = 路由器，备 = 公共 DNS，避免单点）
sudo tee /etc/resolv.conf >/dev/null <<'EOF'
nameserver 192.168.10.1
nameserver 223.5.5.5
options timeout:2 attempts:3
EOF
#   3) 让运行中的 dhcpcd 重读配置
sudo kill -HUP 660
#   4) 验证：连续 20 次采样，size 与 nameserver 行数应恒为 166 / 1
for i in $(seq 1 20); do printf "%s size=%s ns=%s\n" "$(date +%H:%M:%S)" \
  "$(stat -c %s /etc/resolv.conf)" "$(grep -c '^nameserver' /etc/resolv.conf)"; sleep 1; done
```

```bash
# ── 方案 B（备选）：消除「两个 DHCP 客户端同管一块网卡」的冲突 ──
sudo kill 660                                   # 停遗留 dhcpcd
sudo systemctl disable --now dhcpcd 2>/dev/null || true
sudo systemctl restart networking               # 交回 ifupdown
# 之后同样用上面的循环验证 resolv.conf 是否稳定
```

★ **方案 A 与 B 的取舍**：A **不动网络管理归属**、风险最低，**推荐先用**；B 触及网络管理切换，**须在有物理/带外访问手段时执行**（一旦 ifupdown 起不来会断网）。
★ **可选加固**：`sudo chattr +i /etc/resolv.conf`（防再次被覆盖）—— ★ 但**改配置前必须先 `chattr -i`**，否则后续修改会被拒。

**验收判据**：① 连续 20 次采样 `size`/`nameserver` 行数**恒定**；② `grep -c "lookup open.feishu.cn on \[::1\]" logs/app.log` **不再增长**；③ 对账出现**成功**记录（或至少不再报 DNS 错）。

**为什么不能靠代码绕过**：这是**运行环境**缺陷（DNS 解析层），应用无合理手段规避；且**它在"看起来正常"的同时随机失败**，属最危险的一类。★ 值得肯定的是：**本方**把它做成了**可见错误**（明确打出 `[::1]:53` 与完整 URL），**不是静默失败** —— 定位因此只花了很短时间。
