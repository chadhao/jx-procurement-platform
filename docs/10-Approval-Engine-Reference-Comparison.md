# 审批流引擎参考对照与缺口分析（FlowLong / easy-workflow vs 我方转向 ③ 设计）

> **结论先行**：两家参考引擎（Java 的 **FlowLong**、纯 Go 的 **easy-workflow**）在「中国式审批」上的能力**远多于**我方转向 ③ 的设计；但我方**不需要**成为通用工作流引擎——我方是「**11 类固定单据 + 线性审批链 + 会签节点**」的**受控子集**。真正值得吸收的是**四类模型**（节点聚合的四种形态、驳回/重提策略、事件钩子、任务释放位），而非全量功能。**本对照暴露了 3 个必须由用户拍板的产品缺口（G1 驳回重提策略 / G6 催办·超时·提醒 / G5 终止）**，以及 **1 处 `04a` 需修正的既有结论**（`REPLACE` 全量覆盖的方向风险，见 §4）。
>
> **本文只做分析**：不含实现代码、不改业务代码、不新增 migration、**不改 `01a`/`04a` 正文**（需改的列 §7 清单交 team-lead）。⚠️ easy-workflow **硬依赖 MySQL 8.0（用 CTE）** → 我方 **SQLite 不能直接集成，只能参考模型**。

## 2. ★★ 产品缺口清单（G1–G8 核实结果）

> 逐条：**缺口 → 为什么重要 → 对制度的影响 → 建议 → 若要做得改什么**。

### G1 ★★★ 驳回后的「重提策略」（最要命）

| 维度 | 内容 |
|---|---|
| 缺口 | 两家引擎都区分「**回到驳回我的节点继续**」与「**重走全套**」：FlowLong 明列「重新审批执行策略（1 **继续执行** 2 退回驳回节点）」（`README`）；easy-workflow 的「**直接提交到上一个驳回我的节点**」故事原文即「A 改完**直接提给上次驳回他的 E**，B/C/D 不用再参合」。**我方现行定案＝进终态即新单号、全套重走**（`01a` §3 通则 / FR-M9-15 / 用户第二轮口径 ⑤）。 |
| 为什么重要 | ★ **真实低效**：老板（终审 E）反复驳回时，**中间已通过的主管（B/C/D）每次都要重审**——easy-workflow README 原话「不仅效率低，还影响主管领导对员工的情绪」。这是制度落地时**最先被一线抱怨**的点。 |
| 对制度的影响 | 涉及"**驳回后是否重走**"，是**审批制度条款级**问题（不是技术默认）。`01a` §4.4 已把"退回"定性为"审批内部动作"，但**未覆盖"驳回后重提是否跳过已通过节点"**。 |
| 建议 | **列为首位待用户拍板项**。给两条路 + 代价（下表）。 |
| 若要做得改什么 | 若选"继续执行 / 退回驳回节点"：`t_flow_task` 需**保留已通过节点**的通过态（不因驳回清空），并新增"**重提起点**"概念（`resume_from_node`）；`04a` §2 状态机需增"`REJECTED → PENDING`（同单重提）"的**例外路径**——**但该路径与现行"终态锁号 + 新单号"通则冲突**，须用户先裁决"驳回是否＝终态"。 |

| 路线 | 描述 | 代价 | 制度影响 |
|---|---|---|---|
| **甲（现行）** | 驳回＝终态；重提＝**新单号 + 全套重走** | 中间主管反复重审，效率低、情绪差 | 单号简单、审计清晰；**已被第二次口径 ⑤ 写死** |
| **乙（两家引擎做法）** | 驳回＝**回到驳回节点**或**退回发起人**；重提**跳过已通过节点**（或退回驳回节点） | 需"驳回非终态"的例外 + `resume_from_node` + 与"锁号通则"协调 | 需新增制度条款；审计要能表达"同单多轮驳回" |

### G2 ★★ 加签是「前置」还是「后置」、顺序还是并行

| 维度 | 内容 |
|---|---|
| 缺口 | FlowLong 明确区分**前置节点/后置节点**加签（`README`：「增加当前办理节点的办理人员（**前置节点，后置节点**）」）与**顺序/并行会签**。用户只说"加签＝会签"（`01a` §4.3）。 |
| 为什么重要 | "后置加签"（我审完再加人复看）与"前置加签"（先加人再看）在**会签聚合顺序**上不同；若用户实际要"我审完还要别人把关"，我方"同节点并行会签"**表达不了'我之后'的语义**（除非用顺序会签）。 |
| 对制度的影响 | 影响"加签的审批顺序"条款表述。 |
| 建议 | **待用户确认**（低-中）：默认"**并行会签**"（与现设计一致）；若需"后置"，改用**顺序会签**机制（§3.4）。 |
| 若要做得改什么 | `t_flow_task` 增**顺序位** `seq`（已有 `seq` 雏形）与**节点内激活顺序**；推送改为**逐级放开**（§3.4）。 |

### G3 ★★「转办 / 委派 / 代理」三者区分

| 维度 | 内容 |
|---|---|
| 缺口 | FlowLong 把三者**分开**：**转办**（A→B，B 审后进下一节点）· **委派**（A→B，B 审后**回到 A**，A 审后进下一节点）· **代理**（A 授权 B，B 完成后 A、B 都能查，A 完成后 B 看不到）。我方只有"**转交**"（＝转办）与"**代理人**"（`01a` §4.1 表二 / §4.7）。 |
| 为什么重要 | 我方"**代理人**"的语义**未显式对齐** FlowLong 的"**代理**"。若业务含义是"临时全权代做"→ 接近代理；若是"授权某人代我审某单"→ 可能更接近委派。**语义不清会导致权限边界争议**。 |
| 对制度的影响 | "代理人"权责需在制度中写清（是否等同长期授权、是否可再转交）。 |
| 建议 | **待用户确认**（中）：① 我方"代理人"**是否等同** FlowLong"代理"（A 授权 B、A/B 都可查）；② 是否**需要"委派"**（B 审后回到 A）——**采购场景下"委派"少见，建议不做**；③ 是否**需要"离职批量转办"**（结合 `08` 镜像在职态，可低成本实现，建议**可选**）。 |
| 若要做得改什么 | 代理/委派影响 `t_flow_task.assignee` 与"回到原审批人"逻辑；离职转办＝批量"转交"复用既有操作。 |

### G4 ★ 「拿回」

| 维度 | 内容 |
|---|---|
| 缺口 | FlowLong：「当前办理人**未处理前**，允许**上一节点提交人**拿回」（`README`）。我方无。 |
| 为什么重要 | 实务高频：上一节点提交后**发现错了**，在下一节点**尚未处理**时收回重改，避免走"驳回—重提"或"撤回—重发"。 |
| 对制度的影响 | 属"审批内部动作"，与 `01a` §4.4 "已执行不撤回"的**澄清逻辑同源**。 |
| 建议 | **待用户确认**（中）：**建议做**（成本低、体验好）。 |
| 若要做得改什么 | 新增第五个操作"拿回"（主体＝**上一节点提交人**；条件＝下一节点**任一 task 尚未处理**）；沿用四操作框架（服务端硬校验 + `t_flow_op_log` + 重推）。 |

### G5 ★ 「终止」（任意节点终止 ≠ 发起人撤回）

| 维度 | 内容 |
|---|---|
| 缺口 | FlowLong：「在**任意节点**终止流程实例」。我方只有**发起人撤回**（`01a` §4.5）。 |
| 为什么重要 | 制度侧有"违规不撤回、走人事考核"，但**没有"中途终止"**（如发现单据作废、事项取消）。若无终止，只能"撤回"（但撤回仅发起人可做）或走完流程。 |

### 3.1 数据模型对照

| 模型 | FlowLong | easy-workflow | 我方（`04a` §1.1） | 结论 |
|---|---|---|---|---|
| 实例表 | 有（流程实例） | 有 | `t_instance`（真源） | 已有 |
| 任务表 | 有 | 有 | `t_flow_task` | 已有 |
| 节点表 / 流程定义表 | ★ **有**（流程定义 + 节点定义，支持**设计器任意图**） | 有（流程图定义） | ★ **无**：11 类**硬编码/表驱动**（`01a` F4：三方审批定义不含流程定义） | **有意不做**：我方流程是**固定线性链 + 会签节点**，不需要通用"流程定义表" |
| 审批记录表 | 有（审批意见） | 有 | `t_flow_op_log` + `t_audit_log` | 已有 |
| 事件表 | 引擎内 | 4 类事件回调 | — | **建议补**（§3.5） |

### 3.2 会签四种形态 → 我方 `node_id` 聚合映射

| FlowLong 形态 | 我方能否表达 | 实现方式（模型层） |
|---|---|---|
| 并行会签 | ✅ **已表达** | 同 `node_id` 全 task `APPROVED` → 节点通过（`04a` §2.3） |
| 或签 | ✅ **可表达** | 同 `node_id` **任一** `APPROVED` → 节点通过，其余置 `DONE` |
| 顺序会签 | ✅ **可表达（需"逐级放开"）** | 同 `node_id` 按 `seq` **逐级推送**：先只推第 1 人；其通过后再推第 2 人（详见 §3.4） |
| 票签（按权重 >50%） | ✅ **可表达（需权重位）** | `t_flow_task` 增 `weight`；节点通过＝`Σweight(APPROVED) > 50%` |

> ★ **关键结论（正面）**：**四种会签形态均可在"我方聚合"框架内表达**，因为**判定权在我方**（`01a` §4.3 / `04a` §2.3 已确立）。**只需给 `t_flow_task` 增加"顺序位 / 权重位 / 释放位"**，**不需要**依赖飞书 `task_list[].type`。→ 这就是"会签聚合在我方"的**架构红利**。

### 3.3 驳回策略 + 重提策略 → 如何建模

| 概念 | FlowLong | 我方模型（若不采纳 G1 则不做） |
|---|---|---|
| 驳回策略 | 枚举位（1 上一步 / 2 发起人 / 3 任意节点） | 一期＝**仅"上一步"**（`01a` §4.4）；其余二期 |
| 重提策略 | 枚举位（1 **继续执行** / 2 **退回驳回节点**） | ★ **缺（G1）**；`04a` §2 状态机**无 `REJECTED → PENDING` 例外**（现为**终态**） |
| `round` 机制 | — | 我方 `t_flow_task.round` 目前服务**回退重激活**（`04a` §2.3）；若做 G1，可扩展为"**同单多轮**"；但**与"终态锁号 + 新单号"冲突**，须先裁决"驳回是否＝终态" |

### 3.4 ★「顺序会签」在我方能否表达（核查 team-lead 的追问）

> **结论：能，且不需要飞书配合**。做法＝**分段释放（staged release）**：
> 1. `t_flow_task` 增 **`release_state`**（`HELD` / `RELEASED`）与 `node_seq`；
> 2. **快照构造只纳入 `RELEASED` 的 task**（`04a` §3.2 快照 builder 增加过滤）；
> 3. 第 1 人通过 → 释放第 2 人 → **重推**（`REPLACE` 全量，此时才出现第 2 人待办）。
>
> ⚠️ **必须同时满足**：`REPLACE` 全量快照的语义是"**以本次推送为准**"——**未释放的 task 不得出现在更早的快照里**（否则会被后续"不包含它"的快照删掉，或反之混乱）。这要求**释放是单向推进**（只增不缩，符合我方状态机）。
> **代价**：顺序会签下"节点通过时间"被拉长；且**每个释放点都要一次推送**（配额略增，见 `01a` §5.5）。
> **一期建议**：**默认并行会签**（现设计）；**顺序会签作为可配项**（若 G2 用户要"后置加签"再启用）。

### 3.5 事件 / 钩子：是否抽出统一"流程事件"

| 选项 | 结论 |
|---|---|
| 现状 | 通知（`01a` §4.7）、审计（`t_audit_log`）、推送（`04a` §3）、台账（`04a` §5.5/§16）**各自调用**，**无统一挂点** |
| 建议 | ★ **做**（模型层）：定义**流程事件**枚举 + 分发器；**通知 / 审计 / 推送 / 台账** 注册为订阅者 |
| 理由 | 防"新增操作漏挂副作用"（`04a` §10 S2/S11 同族静默）；对齐 easy-workflow 的 4 类事件思想 |
| 代价 | 一次重构（把散落调用收敛）；**不新增飞书能力**，纯内部 |

## 4. 与既有结论的一致性检查

### 4.1 ★ `REPLACE` 全量 + 版本控制的**方向风险**（需修正 `04a §3.1`）

> **team-lead 已查实（另一条线）**：`external_tasks` **不返回操作人/意见**；`check` **只返 diff**；★ **`REPLACE` 不校验 `update_time` 且全量覆盖 → 会把飞书侧已 `APPROVED` 覆盖回 `PENDING`**。

| 项 | `04a` 现结论 | 复查判断 |
|---|---|---|
| `update_time` 递增 | `04a §3.1`：**「每次推送严格递增；不递增 → 推送静默失败」** | ⚠️ **需修正**：据实测 `REPLACE` **不校验** `update_time` → "不递增即被拒"**不成立**（至少未证实）。建议改为：**递增仍是纪律**（幂等/可观测锚点），但**不得依赖"平台会拒"来实现正确性** |
| `REPLACE` 全量覆盖 | `04a §3.1`：一律 `REPLACE` + 全量快照（视为"最可控"） | ★ **需补防护**：全量 `REPLACE` **方向是"我方 → 飞书"**；当**本地快照落后于飞书侧**时，会把飞书侧已 `APPROVED` **覆盖回 `PENDING`**（真实竞态：用户点飞书"同意"→ 飞书侧 APPROVED，但**回调尚未被我方处理**时若触发一次推送/对账，就会回退） |
| 对新设计的影响 | — | ★ **新增防护 S14**（建议加入 `04a §10`）：**推送前必须"以我方最新已处理状态"为准**——① 回调**先落库**再触发任何推送；② 对账**不得**用"落后快照"覆盖；③ 建议推送携带 `update_time` 单调且**对账先读 diff、判断方向**再决定重推（`04a §9.2` 现为"一律以我方重推"，**需细化方向判断**） |
| `external_tasks` 不返操作人/意见 | `04a §9.1`：`external_tasks` 作"任务列表比对" | ✅ **印证**：**飞书侧不是我方审批结论的真相源**（无操作人/意见）→ 对账**只能校验"待办可见性/存在性"**，**不能**用飞书状态反推审批结论。→ 强化"**我方是唯一真相源**"，但**要小心反向覆盖**（见上） |

> **结论（已按 team-lead 裁定定案）**：`04a §3.1` 由"**一律 `REPLACE` + 全量快照**"改为「★ **首选 `update_mode=UPDATE`**（机制消除**状态回退**）、**仅"新增"场景用 `REPLACE`**（首次推 / 新增 task / 新增抄送）」；`update_time` 递增**降级为"纪律、不依赖平台拒绝"**；并列**三级防护**（UPDATE 机制 → 回调先落库 → 对账判方向）+ **QV2-A28**（飞书是否允许 `APPROVED`→`PENDING` 回退）。**已回填 `04a` V1.5**（§3.1 / §9.1 / §9.2 / §9.3 / §10 S14）。

### 4.2 ★「顺序会签」在我方模型可否表达

| 项 | 结论 |
|---|---|
| 会签聚合位置 | ✅ `01a` §4.3 / `04a` §2.3 已定：**在我方**（不依赖 `task_list[].type`） |
| 顺序会签 | ✅ **可表达**（§3.4 分段释放：只推 `RELEASED` 的 task，逐级放开） |
| 并发风险 | ⚠️ 与 §4.1 的方向风险**同类**：顺序会签"逐级放开"更依赖"快照只增不缩"，**与 `REPLACE` 全量语义需一起验证** |
| 与 `01a` 现状 | `01a` §4.3 现只述"并行会签 / 会签＝全部同意"；**未提顺序会签** → 若 G2 用户要"后置加签"，需**新增顺序会签口径**（§7 清单） |
