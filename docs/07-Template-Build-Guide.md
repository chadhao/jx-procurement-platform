## 1. 为什么必须人工建（三条硬依据，非选择） ⛔ **作废（转向 ③ · F5）**

| # | 官方限制 | 后果 |
|---|---|---|
| 1 | `POST /open-apis/approval/v4/approvals`（创建审批定义）**不支持设置条件分支**——官方原文「如需设置条件分支请前往飞书审批后台创建」 | 本方案的审批链**大量依赖条件分支**（按金额分档、按部门决定主管领导、按品类决定验收人），用 API 建出来的模板**根本跑不通** |

> 因此本系统的角色是「**只持 `approval_code` 做映射、只接收事件**」。模板的长相、审批链、条件分支**全部在飞书侧**，改模板不改代码（这正是本方案要的红利）。

## 2. 总流程（5 步） ⛔ **§2①②作废（③·F5）；③～⑤保留**

```
① 人工在审批后台建 11 张模板（含条件分支）
        ↓
② 提交一条测试实例 → 调「获取实例详情」→ 一次性取回 approval_code 与各控件 field_id
        ↓
③ 按样例填 docs/reference/config-mapping.sample.json
        ↓
④ jxapproval import-config --check <file>   # 只校验
   jxapproval import-config <file>          # 落库 + 回读自证
        ↓
⑤ ★ 逐一调「订阅审批事件」（按 approval_code）——漏做则一条事件都不推，且不报错
```

> **② 是关键技巧**：实例详情响应中同时含 `approval_code` 与表单字段数组（每项含控件 `id`）。
> **一次操作即可采集齐全部映射值**，无需在后台页面里找 id。
>
> ⚠️ **可信度声明**：该结构**按飞书官方「获取实例详情」的字段定义实现**（见 `internal/platform/feishu/instance.go`
> 解析 `approval_code` / `form`），但**尚未用真实报文验证**——这正是待确认项 **Q17**。
> 模板首次采集时请**同时记录一条真实响应**，据以确认字段名（若有出入只改适配层一处，不改业务）。

### 3.1 落账列的口径（★ 只能选「实例级」台账）

`t_ledger_archive` 的写入方式是**每个实例一行**（`internal/worker/ingest.go`）。因此 `doc_type → ledger_type`
**只能指向实例级台账**。以下四张**不是**实例级，导入时会被直接拒绝：

| 台账 | 不可指向的原因（架构 §3.4） |
|---|---|
| `L08` 供应商档案与绩效表 | 「本身可写」——**手工维护的主数据**，不随单据产生行 |
| `L10` 用途分类汇总台账 | 「只读」——**汇总**，行由其他台账聚合 |
| `L11` 订单执行台账 | 「数据源＝CT + GR」——**派生**表 |
| `L12` 预算执行台账 | 「保留结构 / 本期不启用」 |

**第 4／5／10 号模板（RFQ／BJ／QC）故意不落账**：它们不构成独立台账，其数据并入对应主单据
（QC 的检验结论并入 `L07` 行）。未配置 → **不写台账**（不虚构口径），这是设计意图而非遗漏。

> ★ **Q14 已定稿（2026-09-26，本节原「待确认」表述作废）**：`L07` 的「检验结论」列取值方式定为
> **「`GR` 与 `QC` 各写一行 + 查询侧按 `related_biz_no` 关联」**——<b>不是</b>「QC 入库时 UPDATE 同一行」。
> 因此配置上：`GR` 配 `related_biz_no`（指向合同/报备单）与 `amount`/`supplier`/`acceptors`；
> **`QC` 必须配 `related_biz_no`（指向其 `GR` 单号）与 `inspection_result`**，
> 否则 `L07` 的「检验结论」列**恒空**。
>
> ★★ **另有一处未闭合的台账生产者缺口（2026-09-27 新发现，须在导入配置前拍板）**：
> 工具表·台账与看板设计 **第 3 号「采购经办登记台账」`L03`** 明确写着数据来源＝「**物资采购申请单**审批节点
> 指定经办人后自动写入」，但系统的 `doc_type → ledger_type` 映射是**一对一**（`Maps.LedgerTypeFor`），
> 而 `PR` 只能指一个台账（样例指 `L02`）→ **`L03` 无人写入**。
> 后果不只是「`L03` 恒空」：看板的「**需求提出人任经办人的笔数**」也读 `L03` → **恒为 0**，
> 而 **0 恰好是该指标的期望值**，「没有违规」与「没有数据」在界面上完全一样。
> **三条候选方案与推荐见** `deliverables/procurement-approval/审批模板人工建立指引V1.1.html` **§12 S-1**。
> 本轮**未擅自改动映射模型**（属设计决策，涉及工具线口径）。

## 4. 控件配置要点（⛔ 4.1/4.2/4.5 作废；✅ 4.3/4.4 改写保留）

### 4.1 流水号控件（11 张都要有） ⛔ **作废（③·F5；编号改由我方生成，见 `04a §6`）**

| 项 | 要求 |
|---|---|
| 控件类型 | 飞书审批「**流水号**」控件 |
| 配置 | 固定字符 = 该单前缀（`BA`／`PR`／…）；提交日期 = 年月（`YYMM`）；自增序号 = **4 位**、按月重置以匹配 `####` |
| 权限 | 流水号控件**不支持审批人编辑**，天然只读 —— 与「自建系统只读单号」一致 |
| 校验 | 提交后不可修改；`YYMM` 是否按月重置属 **Q7**（工具表未明示），建模板时**按「按月重置」建**，若有变只改模板不改代码 |

### 4.2 必须登记映射的控件（否则静默失效） ⛔ **作废（③·F5；原生控件链作废）**

以下控件**必须**在配置文件的 `field_id` 中登记 `biz_field`，否则对应数据**恒空且不报错**：

| 建议 `biz_field` | 控件 | 不登记的后果 |
|---|---|---|
| `amount` | 金额（货币 ¥） | 看板金额类指标全为 0；`spot_check_range` 抽查清单为空 |
| `supplier` | 供应商 | 「同供应商当月累计」防拆分视图失效（**D7 的核心指标**） |
| `purpose_class_l1` / `purpose_class_l2` | 用途分类／二级明细 | `L10` 用途分类汇总无数据 |
| `department` | 申请部门 | 部门维度统计与行级权限（`DEPT` / `CHARGE_DEPT`）失去依据 |
| `contract_no` | 关联合同号（**仅 `PC` 需要**） | **变更链回溯恒为空**（FR-M4-07：按合同号经 `json_each` 检索 `ext_json`） |

> `biz_field` 的合法取值由代码登记（`internal/config/bizfields.go`）：**抽取到规范列** 的 9 个 +
> **透传 `ext_json`** 的若干个。**不在册的名字**导入时会给出提示（多为拼写错误），但不阻断。

### 4.3 金额控件 ✅ **改写保留：改为「我方面单金额校验」**

- 用**货币 `¥` 控件**而非文本，避免用户填 `1,234.56 元` 之类的自由文本（解析器虽兼容，但口径不统一）。
- `PR` 的「预估总金额」应设为**计算列**（公式汇总明细小计，**禁止手填**）——该值是分档判定的唯一依据。
- 金额一律按**元**录入；本系统按**分**入库（解析器已处理千分位、货币符号、四舍五入）。

### 4.4 平台能力边界（决定「哪些靠系统、哪些靠人」） ✅ **改写保留：更新为三方审批边界**

飞书原生审批**不支持跨字段校验**（只有「必填」与「节点级表单权限」两类）。故以下四项**只能靠人工**，
须在模板说明里写死给使用者看：

1. **「指定经办人 ≠ 需求提出人」**——审批节点指定后，由综合运营主管在**三单匹配初审**人工核对；
2. **经办人可指定范围**——由主管领导指定时把握（跨部门须经被指定部门主管领导同意，D2）；
3. **到货验收人构成**——按品类三组由人工把握（A2）；
4. **「默认值」不可设为只读**——部门／联系人控件即使设了默认值，**发起人仍可修改**：
   在**模板说明**里写死「**不得改为他人／他部门**」，并把「部门＝发起人部门」当**校验项**而非信任项；
   「主管领导是谁」改用**条件分支的「发起人部门条件」**而非表单值（见可交付版指引 §5 分支二）。

> 这四项是**平台无能力的已知替代**，不是遗漏。台账侧用「需求提出人任经办人的笔数（应恒 0）」+
> 「经办人指定集中度」两个指标做**事后**兜底；默认值可改则由**部门维度统计与行级权限**（`DEPT`/`CHARGE_DEPT`）兜底。

### 4.5 联系人控件 与 部门控件 ⛔ **作废（③·F5）**

- ★ **飞书审批没有「人员」控件**：要选人只能用 **「联系人」**控件，要记录部门只能用 **「部门」**控件——
  这是**两个独立控件**，不要混写成一个「人员／部门」。
- **「联系人」控件**：默认值类型可选「**申请人**（即发起审批用户）／指定人员」；
  用于「申请人」的显示与「指定采购经办人／签署人／验收人」的填写。
- **「部门」控件**：默认值类型可选「**申请人部门**（即发起审批用户所在部门）／指定部门」；用于「所属部门」（`department`）。
- ★ **默认值设置的位置**：**点击控件后，在右侧「基础设置 → 默认值设置」**里配置——**不在左侧控件面板里**
  （这正是「找不到在哪里带入当前登录人／部门」的原因）。
- ★ **默认值 ≠ 只读**：飞书帮助中心《表单控件支持设置默认值》与飞书官方《为控件设置默认值 API 说明》两处都明确
  「**支持员工在发起表单时修改**」，故部门／联系人控件**可被发起人改动**。
  凡「必须等于系统值」的字段，须在**模板说明**里写死约束并做事后核对（见 §4.4 第 4 项）。
- **「申请人」这个数据本身不需要表单控件**：审批实例**自带发起人**（`open_id`／`user_id`，
  `internal/platform/feishu/instance.go`），`applicant_open_id` **直接取实例**；
  表单上若要**显示／引用**申请人，才用「**联系人**」控件并把默认值类型设为「申请人」。
  而**「所属部门」必须有「部门」控件**——`department` **只能来自控件值**（`internal/worker/extract.go`），取不到就无法落库。
- **「主管领导是谁」不要依赖表单里的「部门」控件**（可被发起人改）→ 用**条件分支的「发起人 → 部门」条件**
  （官方 Default field＝发起人，身份不可被改；详见可交付版指引 §5 分支二）。
- **「验收人」用可多选的「联系人」控件**（三组人数不同：2／3／2）。
- 用途分类用**单选枚举**，选项为 23 个一级分类（`P01–P08` / `S01–S07` / `M01–M08`），
  二级明细**必填**（一级只用于汇总，二级才是审计核查依据）。

## 5. 采集 `approval_code` 与 `field_id` ⛔ **作废（③·F5；`field_id` 映射作废）**

| 值 | 采集方式（推荐顺序） |
|---|---|
| `approval_code` | ① 提交一条**测试实例** → 调实例详情接口 → 读响应 `approval_code`；② 或从审批后台审批定义页取得 |
| `field_id` | **同一份响应**的 `form` 数组里，每项的 `id` 即控件 `field_id`，`name` 为控件显示名 |

> ★ **先把一条真实响应原样存下来**（脱敏后存 `docs/reference/`），它同时解决 **Q17**（报文版本与幂等字段）
> 与本节（`approval_code` / `field_id` 命名）。**不要在未验证字段名的情况下批量填映射**。

**采集注意**：

- 模板里**每一个**控件都会出现在 `form` 中，**只挑要映射的那几个**登记；其余字段仍会落 `t_instance_field`（不丢数据）。
- 同一 `field_id` 在不同模板可能含义不同 → 映射键是 **(doc_type, field_id)**；跨模板同义的控件可用
  `doc_type: ""` 的**全局映射**。
- **提交一条测试实例是必要的**：模式 A 下本系统不能建实例，必须由人在飞书里提交一次。
  测试实例可用 `BA`（采一档）——它不签合同、不转账，副作用最小。

## 6. 生成配置文件并导入 ✅ **保留 + 新增 `approval_code → 单据类型` 反向映射**

以 `docs/reference/config-mapping.sample.json` 为模板填写。样例含**五类**映射：`approval_code`(11) / `field_id`(9) / `ledger_type`(**9**) / `threshold`(5) / **`ledger_field`(16)**。该样例**故意带 `REPLACE_ME` 占位符**，
**未替换前导入会被直接拒绝**——这是刻意设计的护栏（同一批错配置写进去的后果是「模板永远订阅不到事件、
系统一条数据都没有、且没有任何错误日志」）。

```bash
# ① 只校验，不写库（填完后先跑这个）
jxapproval import-config --check /path/to/config-mapping.json

# ② 落库 + 回读自证（导入后会按 approval_code 反查单据类型，并对未登记字段名给出提示）
jxapproval import-config /path/to/config-mapping.json
```

**成功输出形如**：

```
配置映射导入完成：approval_code 11 / field_id 9 / ledger_type 9 / threshold 5 / ledger_field 16，合计 50 条；db=/var/lib/jxapproval/app.db
已全量替换映射类：approval_code, field_id, ledger_type, threshold, ledger_field
台账字段定义 16 条已写入 t_ledger_field_def：写接口据此校验 fields 键名（该台账无登记则不校验）
回读校验通过：11 条 approval_code 均可反查单据类型
```

**同时会打「非阻断提示」到 stderr**（示例为按样例文件原样填充后的实际输出）：

```
注意：以下 3 个阈值键已登记但**当前无消费端**（写入后不改变任何行为）：emergency_hours, purchase_tier, submit_workdays
      当前真正生效的阈值键：split_supplier_month, spot_check_range
      这是「假配置」提示，非错误；口径可先行登记，待对应功能实现后自动生效。
```

**失败即整体拒绝**（不做部分导入）。常见拒绝原因与对策：

| 报错 | 含义 | 对策 |
|---|---|---|
| `仍是未替换的占位符` | 样例没填 | 填入真实 `approval_code` / `field_id` |
| `doc_type 必须是 …` | 前缀写错 | 只能是 11 个前缀之一 |
| `value 必须是 … 不能作为单据的落账目标` | 台账指向了汇总／主数据／派生／未启用台账 | 改指实例级台账，或**留空不落账** |
| `field_id 重复` | 同 (doc_type, field_id) 出现两次 | 删掉重复项 |
| `threshold … 必须是数字或「左-右」区间` | 阈值格式错 | 写 `1000` 或 `800-1000` |

**另外两类「非阻断提示」必须读**（打到 stderr，导入仍成功）：

| 提示 | 含义 | 为什么必须看 |
|---|---|---|
| **`biz_field` 不参与规范列抽取** | 该名字既未登记为「抽取列」、也未登记为「透传 `ext_json`」 | **多为拼写错误**。把 `amount` 写成 `amout` → 金额列**恒空**、看板与防拆分失效，**却不报错** |
| **阈值键当前无消费端** | 该阈值已入库，但**代码目前不读它** | 这是「**假配置**」：以为设了 `purchase_tier` 就实现了分档，实际不改变任何行为 |

**阈值键消费现状**（截至本版）：

| 阈值键 | 消费端 | 状态 |
|---|---|---|
| `split_supplier_month` | 看板防拆分视图 + 台账红标 | ✅ 已消费 |
| `spot_check_range` | 台账抽查区间红标 | ✅ 已消费 |
| `purchase_tier` | — | ⚠️ **未消费**（仅口径登记） |
| `emergency_hours` | — | ⚠️ **未消费** |
| `submit_workdays` | — | ⚠️ **未消费** |

> `enum.*`（状态 / 单据类型 / 结算状态枚举，架构 §6.3）**故意不在导入范围内**：当前枚举值写在代码里，
> **没有消费端**。若把 `enum` 也做成可配而无人读，就是重现「配了、没人读」的同类缺陷——**故不做**，
> 待枚举收敛为数据驱动时再一并加。

## 7. ★ 订阅审批事件（最易漏、后果最重） ⛔ **作废（转向 ③ · 无审批事件；F1）**

**必须按每个 `approval_code` 逐一调用「订阅审批事件」。** 漏做任一模板的后果是：

> 该模板的审批事件**一条都不会推送**，系统里**永远没有这张单据的数据**，**而且不报任何错**
> ——「静默无数据」。

| 项 | 要求 |
|---|---|
| 调用粒度 | **按 `approval_code` 逐个**（不是按应用一次性订阅） |
| ★ 订阅范围 | ★ **只订阅 `approval_instance`（实例级）**。`approval_task`（节点级）**本期不订阅**（PRD §3.2 **N10**）——订阅了却没有处理逻辑，只会凭空增加事件量与失败面 |
| 调用时机 | 映射导入**之后**（订阅需要 `approval_code`） |
| 订阅状态 | 落 `t_subscribe_state`，可单点查询；启动时自检 |
| 传输方式 | 长连接 WebSocket（无需公网 IP／入站端口／白名单，**仅企业自建应用**） |
| 部署约束 | **单实例**（集群模式**不广播**，多实例只有一个随机实例收到事件） |
| 处理时限 | 事件须 **3 秒内**处理完，否则超时重推（15 秒 / 5 分钟 / 1 小时 / 6 小时，最多 4 次） |
| 幂等 | 平台「**至少投递一次**」→ 幂等键必须用**事件级唯一 ID**（2.0 版 `header.event_id`、1.0 版顶层 `uuid`），**不是** `instance_code + status` |

## 10. 模板变更管理

改模板**不需要改代码**（本方案的核心红利），但**必须**同步检查三处：

| 变更动作 | 需要做什么 |
|---|---|
| 新增控件 | 若要抽取该字段 → 在配置文件增一条 `field_id` 映射并重跑 `import-config`；否则无需动作（自动落 `t_instance_field`） |
| 控件**改名** | 映射键是 `field_id` 不是显示名，**显示名改名不影响**（这正是用 id 而非中文名匹配的原因） |
| 删除控件（换新 id） | 删掉旧映射行、加新映射行并重跑导入；历史数据不受影响 |
| 新增模板 | 建模板 → 采集 `approval_code` → 加映射（含 `doc_type`，需在 `DocTypes` 白名单内）→ **单独订阅** → 重跑导入 |
| 审批链调整 | 无需改代码；但若改变「湖南侧截止到项目总经理」等**制度口径**，须同步改制度与工具表（工具线） |
