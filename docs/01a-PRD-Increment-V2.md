## 3. 单据编号规则（★ 必须重新定义）

**背景**：原设计单号由飞书**流水号控件**生成、我方只读（`README` 决策 #5 / `07` §4.1）。三方审批定义**不含表单控件**（无流水号控件）→ 单号必须改由**我方生成**。

| 规则点 | 定义 | 理由 | 代价 / 例外 |
|---|---|---|---|
| 格式 | 沿用 `{前缀}-{YYMM}-{####}`（前缀沿用 `BA/PR/SA/RFQ/BJ/SS/CT/PC/GR/QC/SUB` 11 类；PO 沿用 `CT`，Q6 不变） | 保持工具表·单据清单口径与既有台账 / 看板 / 检索不改 | 无 |
| `YYMM` | 业务本地年月（Asia/Shanghai），与 `biz_date` 同源 | 与 `01-PRD` 决策 #33（`biz_date=YYYY-MM-DD`）一致，避免跨时区串月 | 无 |
| `####` | 4 位十进制自增；**按月重置**（沿用 Q7 默认口径，Q7 未定则按此建，若有变只改配置） | 与 `07` §4.1 原配置一致 | 若 Q7 最终为"不重置"，仅改配置 |
| 生成时机 | 提交页**点"提交"通过校验后**由我方生成，**同事务写入 `t_instance.biz_no`** | 单号即业务唯一键 + 幂等锚点（`README` 决策 #11） | 无 |
| 并发唯一 | 单实例 + SQLite：事务内对 `t_doc_seq(doc_type, yymm)` 读改写；表级 `UNIQUE(biz_no)` 兜底，冲突则重试 | 单实例下无分布式竞态；唯一索引防"序列错乱导致重号" | 事务须短（`01-PRD` FR-M8-09） |
| 与「撤回后重新发起」的关系 | ★ **通则**：**任何进入终态的单号永久不复用** —— 终态 = `APPROVED` / `REJECTED` / `CANCELED`（**通过 / 拒绝 / 撤销都算**）；再次发起**必须**用新单号（`####` 递增） | 用户第二轮口径 ⑤ 明文；原"撤回后重发＝新号"由**特例提升为通则**（"拒绝后重提"同理，沿用 `01-PRD` FR-M3-05 原单留痕） | 单据数随拒绝 / 撤回而增多，属预期。★★ **已定案（V1.8 · 用户第四轮口径 ①，见 §9 `G1`，**不再待拍板**）**：`REJECTED` 后现行＝"**整套重走（新号）**"，另一方案＝"**继续执行**（驳回**不进终态**、可回到驳回节点）"——**后者与本行"进终态即锁号"冲突、须改模型**，**故已被用户否掉**、锁号模型**无需改动** |
| ★ 锁号实现（**不新增"已用号"表**） | ∵ `t_doc_seq(doc_type, yymm).last_seq` **单调递增** + `t_instance.biz_no` **UNIQUE** + **实例永不硬删除**（撤回＝软状态 `CANCELED`，仍占号）→ **"单号永久不复用"已被现有约束覆盖**，**不引入独立 `t_biz_no_used`** | 独立"已用号"表会与 `UNIQUE` 形成**两处真相**（正是本仓库在防的静默模式）；且违反决策 #24「新增配置键 / 表须有**独有**消费端」 | 若将来出现"**硬删除后仍需锁号**"的新需求才引入（当前无）；跨月由 `YYMM` 键天然隔离 |
| ★ 负向断言 | **试图复用（终态）单号必须被拒**：由 `t_instance.biz_no` **UNIQUE** 拦截（命中 → **拒绝 + 告警**），**绝不静默分配同号** | "永久不复用"由**数据库唯一约束**强制，不靠应用侧"记得别复用" | — |
| 旧单留痕（终态通用） | 旧单**不删除**，状态置「**已撤回**」/ 保留「已驳回」（见 §4.5）；台账 / 审计按单号可查两单因果关系（`new_biz_no` ← `prev_biz_no`） | 审计要"撤回 / 拒绝前发生过什么"可回溯 | 需新增"已撤回"状态枚举（§8 FR-M9-10） |
| 与 `instance_id` 关系 | 我方 `instance_id`（推给飞书的实例标识）**取 `{app_id}:{biz_no}`**（企业+应用内唯一） | 单号唯一 + **应用前缀** → 消除"多环境/多应用复用同一应用静默撞 ID"（撞 ID = **审批中心空白、无任何异常**）；一个字段同时承担"业务号 + 三方实例号"，减少对账错位 | ★ 须确认本系统与其它系统是否共用同一个飞书应用（QV2-A21）；即便独立应用也保留前缀，为后续多环境留余量 |

> ★ **`####` 是否按月重置** = 原 `01-PRD` Q7（仍待工具表确认）；本文沿用"按月重置"作为默认。

## 4. ★ 四个操作的产品规则（本文核心新增）

> **前提事实（brief §3.4）**：飞书快捷审批**只回调 `APPROVE` / `REJECT` 两种**（`action_type`）；**转交 / 加签 / 回退 / 撤回在飞书侧没有任何按钮和回调**，只能在我方发起。以下四项**在制度中零定义**（见 §4.5），故全部标注 **「新增，需管理层确认」**。

### 4.1 四个操作总览

| 操作 | 发起人 | 飞书侧表现 | 我方 `update_mode` | 是否新增制度条款 |
|---|---|---|---|---|
| 转交 | 当前节点审批人本人 **或其代理人** | 原任务 `status=TRANSFERRED`；新审批人 task 进其待办 | `REPLACE`（**纯新增 task**） | ★ 是 |
| 加签 | 当前节点审批人本人（**代理人不可加签**） | 新增 task（**顺序会签 · 轮到才推**）进被加签人待办 | `REPLACE`（**纯新增 task**） | ★ 是 |
| 回退 | 当前节点审批人本人 **或其代理人** | 被回退节点的 task 重新置 `PENDING` 并进待办 | **`UPDATE`**（状态变更，§6.1） | ★ 是（且须处理与既有条款的冲突，见 §4.4） |
| 撤回 | **仅发起人本人**（**代理人不可撤**） | 实例 `status=CANCELED`（关闭流程） | **`UPDATE`**（状态变更，§6.1） | ★ 是 |

**§4.1 表二 · 操作 × 主体权限矩阵**（★ 用户第二轮口径 ⑥ 定案）

| 主体 \ 操作 | 转交 | 加签 | 回退 | 撤回 |
|---|---|---|---|---|
| 当前节点审批人本人 | ✅ | ✅ | ✅ | —（非发起人） |
| **其代理人**（★ **仅其所代理的那个节点**） | ✅ | ❌（不开放） | ✅ | ❌（不开放） |
| 发起人（申请人） | —（非审批人时） | — | — | ✅（唯一） |
| 其他审批人 / 无关人员 | ❌ | ❌ | ❌ | ❌ |

> 规则：**代理人权限 = 转交 + 回退；不含加签与撤回**（口径 ⑥ 只放"转交 / 退回"）。★★ **术语统一（第三轮 ⑤-4）：「退回」与「回退」＝同一动作，本文一律用「回退」**（"退回"仅作历史用词保留）。
> ★★ **代理人范围（第三轮 ⑤-3）**：**代理人仅能操作"其所代理的那个节点"**，**不得越节点**操作其他审批人的任务。
> ★ **代理人或本人行使转交 / 回退时，必须通知该单内"已审批通过"的所有人**（见 §4.7）。
> ★★ **术语澄清（第四轮口径 ③ · V1.8）**：用户明示「**只有"转办"，没有"委派"**」——① 本文 **§4.2「转交」（Transfer）＝ 用户所称「转办」**（同一动作，与上列"退回 / 回退"同理）；② ★ **不做「委派」**（FlowLong 的"**B 审后回到 A / 会后回任**"）→ 状态机**不引入"会后回任"**；③ **原 `G3` 第①问**（我方"代理人"与 FlowLong"代理"**语义是否对齐**）**降级为技术项**——**语义对齐不影响本表二的权限口径**（本表二以**用户口径 ⑥**为准：代理人**可转交 + 可回退；不可加签 / 不可撤回**）。来源：用户第四轮口径 ③（§1.6）。

### 4.2 转交（Transfer）

| 规则点 | 规则 | 理由 | 例外 / 代价 |
|---|---|---|---|
| 谁能转交 | **当前节点审批人本人**，**或其代理人**（该 task `assignee=me`，或"我是该审批人的在册代理人"；且 `status=PENDING`）；★ **代理人仅能转交其所代理的那个节点**（第三轮 ⑤-3） | 转交是处分审批权的行为；★ 口径 ⑥ **明确放开代理人**（原"待管理层确认"已定案） | ★ **代理人或本人转交时须通知**该单内已审批通过的所有人（§4.7）；仍**禁止转交给申请人本人**（回避） |
| 转交给谁 | 任意**在职且未停用**的员工（取自通讯录镜像，§7） | 审批人可能休假/出差，需临时移交 | 建议**禁止转交给申请人本人**（回避，`01-PRD` §4.4）；越权风险由镜像在职校验兜住 |
| 是否限本部门 | **不限**，但记录"转出部门 → 转入部门" | 跨部门协办常见（如生产→质检） | 副作用：跨部门转交须留痕备查 |
| 转交后飞书表现 | 原 task `status=TRANSFERRED`；**新增**一个同 `node_id` 的 task 给新审批人（进其"待办"） | 用户口径 4：转交要"在飞书上同步推送相关人员" | 需保证 `task_id` 在实例内唯一（§6.2） |
| 能否再转交 | **允许**（链式），但**每单转交次数上限 = 3**（可配） | 防"击鼓传花"式推诿；链式轨迹可查 | 上限触顶 → 拒绝并提示"请改用回退或加签" |
| 转交后原审批人 | **不能再操作**该节点（task 已 `TRANSFERRED`） | 权责清晰，避免双人重复审批 | 若原审批人反悔 → 只能由新审批人再转交回来 |
| 留痕 | 写 `t_audit_log` + 状态史：`转交(转出人→转入人, 时间, 原因)`；台账"当前节点审批人"随之更新 | 审计要能回答"这单为什么换人" | 原因是否必填 → 建议**必填**（`action_configs` 控制飞书侧是否要原因，但我方页面自采） |

### 4.3 加签（Add-sign）

|---|---|---|---|
| 谁能加 | **仅当前节点审批人本人**（`PENDING`） | 同转交 | 无 |
| 加给谁 | 任意在职且未停用员工（通讯录镜像） | 补充专业意见 / 共担责任 | 禁止加给申请人本人（回避） |
| **会签 = 顺序会签（★ 第三轮定案：不是并行）** | ★ **加签 = 会签，且为「顺序会签」**（用户第三轮原文：「**加签是顺序会签，上个人审批之后，下个人才能收到通知。**」）：**同一 `node_id` 下多个审批人逐级放开**——**当前人"可办理"、其余人"未激活"**；前者**同意后**才**激活下一个**并重推。会签聚合仍是「按 `node_id` 聚合全部 `APPROVED`」，但**输入由"并行收集"变为"顺序链"**。★ **会签聚合实现于我方** | 加签若只通知不阻塞＝无效加签；**顺序会签**符合"上个人审批之后下个人才收到通知"的既有制度直觉；本架构**流转决策权在我方**，顺序链只是我方聚合逻辑的一个分支 | **`task_list[].type` 仅影响飞书侧展示形态**，**不影响流转正确性**。★ 若平台不支持该字段 → 仅飞书侧不显示会签组，**功能不受影响**（非功能降级，无需告知用户）。★ **新增待实测（并入 QV2-A27）**：**`task_list` 里"未激活 / 未释放"的 task 会不会在飞书侧也生成待办**（若会 → 顺序会签的"下个人才收到通知"在飞书侧不成立，须在推送时机上规避：**逐个激活才推该 task**） |
| ★ **加签时机：前置 / 后置（★ V1.8 定案 · 用户第四轮口径 ②）** | ★ **已定**：**前置与后置都支持**，由**操作人当场选择**，**默认后置**。① **前置加签** ＝ 在「我」**之前**插入审批人（**先加者先审**）；实现＝新 task 的 `task_order` 取「当前办理人 order」，**同节点 `order ≥` 该值者整体 +1**（**已 `APPROVED` 者不动、不重审**），重推后**新 task 排在当前办理人之前**；② **后置加签** ＝ 「我」**审完后再加人复看**（**后加者后审**）；实现＝新 task 的 `task_order` 取**本节点 max + 1**。★ 两者**均不得使已 `APPROVED` 的任务重审** | 用户第四轮原文：「**加签前置后置都支持**」；顺序会签已定（上一格），前置 / 后置只是**在顺序链上的插入位置不同**（前置插到当前人之前、后置追加到其后） | **默认后置**；`node_seq` 扩展位**继续保留**（供二期并行 / 票签），但**前置 / 后置本身不再依赖扩展位**（本期实现） |
| 加几个 | **每节点加签上限 = 3**（可配）；节点总人数受 `task_list` max 300 硬约束 | 防节点无限膨胀 | 触顶拒绝 |
| 节点状态如何算 | **顺序会签**下：按顺序**逐个激活**；节点 = **所有 task 均 `APPROVED`** 才 `APPROVED`；**任一 `REJECTED` → 节点 `REJECTED`**（**后续"未激活"task 一并终止**）；**"未激活"task 不计入"待办"**（推送时机见上格） | 与"顺序会签"定义一致 | 会签下原审批人不能"先走"；★ **"未激活" task 是否在飞书侧出现 = QV2-A27 新问** |
| 飞书侧体现 | ★ **顺序会签下**：新加 task **先"未激活"**，**轮到它时才推**（进待办 + 通知）；`action_configs` 控制飞书按钮与是否必填原因/附件 | 用户第三轮："上个人审批之后，下个人才能收到通知" | 飞书侧只呈现按钮，真实流转在我方 |
| `update_mode` | **`REPLACE`（纯新增 task）+ 传我方完整快照**（含原 task + 新 task） | 加签＝**纯新增 task** → `REPLACE` 安全；`REPLACE` 会删掉"本次未推送"的任务/抄送 → 传全量即安全；见 §6.1 | 每次须携带全部 task/cc（≤300/≤200） |
| 加签后可否撤回加签 | **一期不做**（须人工回退整个节点） | 减少状态机复杂度 | 列入 §9（是否需"减签"） |

> ★ **`task_list[].type` 的三种情形（★ 三分 · team-lead 裁定）**：判定点不是"字段可不可忽略"，而是「**谁在做节点聚合判定**」。**判定权在我方 → 只要平台不替我判，会签就成立。**

| 情形 | `task_list[].type` 的行为 | 会签功能 | 处置 |
|---|---|---|---|
| **A** | **可忽略**（不传也不报错） | ✅ 不受影响（我方按 `node_id` 聚合） | 不传；飞书侧可能不显示"会签组"（**展示差异**，无需告知用户） |
| **B** | **必填**，但只是**展示提示**、飞书**不据此自行聚合** | ✅ **不受影响** | 必须传（取"会签 / AND"对应值）；我方聚合仍为准 |
| **C** ★ | **必填**，且**飞书据此自行聚合**（如传"并签 / OR"后**任一同意即关闭同节点其他 task**） | ❌ **真功能降级**（我方会签被平台截断） | ① 平台**有**"会签 / AND"取值 → 传 AND，**功能保住**；② 平台**只有 OR 且会提前关闭** → **才是真降级**，**此时必须告知用户** |

> **补充**：因**缺必填字段**导致 **推送 400**，归入"**我方请求有误**"（走失败重试 / 阻断 / 告警），**不等于**"会签不支持"——**不得**把"接口 400"误判成"会签不支持"。真正的"会签不支持"**只有情形 C 的后半段**。三情形与 `type` 是否必填 = **QV2-A27** 实测。

> ★ **扩展位（本期不启用，★ V1.4.1 team-lead 裁定）**：`t_flow_task` 的 `weight` / `node_seq` **保留**——**二期若需票签 / 并行会签，按扩展位实现**；**本期不可配**。理由：用户定案"**加签＝顺序会签**"，引入"可配并行"会让"**逐级释放**"的实现分叉（并行要一次释放全部），**无需求不开此口子**。（`04a §2.3` 已同步改"本期不可配"。）

### 4.4 回退（Rollback）

| 规则点 | 规则 | 理由 | 例外 / 代价 |
|---|---|---|---|
| 谁能回退 | **当前节点审批人本人**，**或其代理人**（`PENDING`）；★ **代理人仅能回退其所代理的那个节点**（第三轮 ⑤-3） | 同转交；★ 口径 ⑥ **明确放开代理人**（用户用词为"退回"，与本文"回退"同一动作） | ★ **代理人或本人回退时须通知**该单内已审批通过的所有人（§4.7） |
| 回退到哪 | **一期只支持"回退到上一节点"**（不支持指定节点 / 回退到发起人） | 覆盖 95% 场景，状态机可控 | 「指定退回到某节点 / 退回发起人改单」→ 二期（§9） |
| 回退次数 | **每单回退上限 = 2**（可配） | 防无限打回 | 触顶拒绝并提示 |
| 已被审批节点是否重新激活 | **重新激活**：被回退节点（及其后续节点）task 置回 `PENDING` 并进待办；已产生的历史**不删除**、追加记录 | 回退后需重新审，历史要能回看"曾审过一次" | 状态史需支持"同节点多轮" |
| 飞书侧体现 | **`UPDATE`**（状态变更）：被回退节点 task 回 `PENDING`，重新出现在审批人"待办" | 用户口径 4：回退要"在飞书上同步推送相关人员"；回退是**状态变更**非纯新增（§6.1） | 无 |
| ★ 与「已执行的操作不撤回」条款冲突 | **必须显式处理**：制度第五十八条原语境是「**违规行为**已执行的操作不撤回，按人事制度考核」，**不适用于流程回退**。回退是"审批内部动作"，与"违规不追回"是两件事 | 若不区分，会被读成"系统违反制度第五十八条" | **新增制度条款，需管理层确认**：明确"第五十八条的'不撤回'指违规处分与已付款，不含审批流程内的回退/撤回" |

### 4.5 撤回（Cancel）

| 规则点 | 规则 | 理由 | 例外 / 代价 |
|---|---|---|---|
| 谁能撤 | **仅发起人本人**（申请人）；**代理人不可撤** | 撤回是发起人的处置权；★ 口径 ⑥ 只对代理人放开"转交 / 回退"，**不含撤回** | ★ **代理发起场景的出路（第三轮 ⑤-6；team-lead 按授权定稿，用户可事后调整）**：代理人**不可**撤回；出路＝① 代理人**把任务转交回发起人**（再由发起人行使撤回），或 ② **通知发起人自行撤回** |
| ★ 发起入口（口径 ①） | **我方页面**（"我的申请"详情页点「撤回」）；该页面**在飞书内打开**（§5.1）；飞书侧**无撤回按钮** | 用户口径 ①"撤回就是 canceled，**app 里点**，同步到飞书没问题" + 口径 ②"呈现是**飞书内的 web 页面**" | 飞书侧只体现"关闭"结果（`CANCELED`），不承载撤回按钮（平台事实：快捷回调仅 `APPROVE`/`REJECT`） |
| 什么时点可撤 | ① **审批完成前**（实例 `PENDING`，不论是否已有人审批）**均可撤**；② **终态后不可撤**（`APPROVED` / `REJECTED` / 已 `CANCELED`） | 口径未限制"已审批不可撤"；发起人应能随时收回 | ★ 有人已审批后撤回 → 已审记录保留在状态史（不丢证据），但该审批作废 |
| 撤回后飞书侧 | 实例 `status=CANCELED`（**关闭当前审批流程**）；相关 task 从"待办"消失；★ **该状态由我方主动推送同步**（非飞书端发起） | 用户第二轮口径 ①"撤回就是 canceled，app 里点，同步到飞书没问题"；口径 4 原句"在飞书端关闭"应理解为**结果表现为关闭**（我方推 `CANCELED`），而非飞书有撤回按钮 | 飞书侧"关闭"= 状态置 `CANCELED`，**不是删除** |
| 重新发起 | **用新的审批单号**（§3）；新单与原单不合并、不继承 | 用户口径 4 明文 | 申请人须重填（或从旧单"复制发起"，**一期可不做**） |
| ★ 旧单台账留痕 | 旧单**不删除**；台账新增「**已撤回**」状态口径（与「已驳回」并列）；字段 `prev_biz_no` 记旧号、`cancel_reason`、`cancel_at` | 审计要能回答"撤了几次、每次为什么" | 需新增状态枚举 + 台账列（§8 FR-M9-10 / §10 04） |
| 撤回是否需理由 | 建议**必填原因**（我方页面自采） | 频繁撤回是异常信号，可入看板预警 | 无 |

## 5. 飞书交互形态

### 5.1 审批人在飞书看到什么（★ 口径 ②③ 定案：飞书内 Web 页面 + 只展示基本信息）

> ★ **正面结论（取代原"预期差"表述）**：用户要的只是**基本信息**（什么人 / 什么部门 / 审批什么项目），这与 `form` **只展示前 3 条、≤2048 字符**的平台限制**正好吻合**——这**不是缺陷，而是设计口径**：**不追求在飞书里呈现完整单据**，完整内容一律在**飞书内嵌的我方 Web 页面**。

| 项 | 规则 | 依据 / 理由 |
|---|---|---|
| ★ 呈现形态（口径 ②） | **呈现效果 = 飞书内的 Web 页面（我方页面）**；`display_method` 写定为 **`SIDEBAR`（侧边抽屉）** | 用户明确"呈现的效果肯定是飞书内的 web 页面"；`SIDEBAR` 不打断飞书上下文；`TRUSTEESHIP` 作**备选**（若 `SIDEBAR` 实测不可用）→ 列入 §9（QV2-A26） |

## 6. 一致性与对账

### 6.1 `update_time` 递增 + `update_mode` —— **默认 `UPDATE`，`REPLACE` 仅限"纯新增"**（★ V1.4.1）

> 事实（brief §3.3）：`REPLACE`（默认）**全量替换**，会**删掉本次未推送的多余任务 / 抄送**；`UPDATE` **增量、不删**；每次 `update_time` 必须**递增**；官方 FAQ 明确**「不能只更新审批状态」**（须传全量字段）。

**① 为什么"默认 `UPDATE`"（★ V1.4.1 定案）**

> ★★ **"落后才 `UPDATE`"这个方案本质上不可实现** —— 要判断"我方是否落后"，就必须知道**飞书侧的当前状态**；而 `external_tasks` 与 `external_instances/check` **都不返回操作明细 / 操作内容**（前者只有粗粒度 `status` + `update_time`，后者只返 `diff_instances`）。**我们拿不到"是否落后"这个信息 → 就做不出这个判断 → 因此不能把 `UPDATE` 设为条件分支，只能设为默认。**
> ★ 推论：**默认 `UPDATE`**（`update_time` 严格递增）；**`REPLACE` 仅限"纯新增"场景**（此时飞书侧**无既有状态可被覆盖**）。

**② 场景选择（`update_mode`）**

| 场景 | 结论 | 理由 / 代价 |
|---|---|---|
| ★ **默认（状态变更：同意 / 拒绝 / 回退 / 撤回 / 恢复与对账重推）** | ★ **`UPDATE`**（增量；`update_time` 严格递增） | 机制上**天然拒绝"落后快照覆盖"**（官方语义＝`update_time` 变大才更新）；不依赖"人记得先判断方向"（而方向本就判不了，见①） |
| 首次推实例 | `REPLACE`（**纯新增**） | 飞书侧**无既有状态可被覆盖**，`REPLACE` ＝ 建立 |
| 新增 task（**加签 / 转交**） | `REPLACE`（**纯新增**） | 同节点**只增**，`REPLACE` 全量 ＝ 补齐，**不涉及"回退既有状态"** |
| 新增抄送 | `REPLACE`（**纯新增**） | 同上 |

**③ `REPLACE` 场景下的【必要条件】**（与②是两件事，**各管一段**）

> ② 决定"**用哪个 `update_mode`**"；③ 是"**一旦用 `REPLACE`，必须满足的条件**"——两条**不矛盾**（对齐 `04a §10 S3`）。
>
> ★ **编号消歧（README 定案 #56；登记见 `15-Code-Collision-Register.md` §2 行 8）**：本文凡引 `S…` **均指 `04a §10` 静默防护清单** `S1`–`S15`；★ **与 `08 §4.9` 的 `S…`（**部门 ID 改造位点** `S1`–`S24`）不是同一个**（两族 `S1`–`S15` 区间重叠），引用请写明来源（「`04a §10 S3`」）。

| # | 要求 | 说明 / 代价 |
|---|---|---|
| 全量 | 用 `REPLACE` **必须携带"我方完整实例快照"**（全部 `task_list` ≤300 / `cc_list` ≤200） | 否则**未包含在本次请求的数据（实例 / 任务 / 抄送 / 节点）会被清空、替换**（官方语义） |
| 超限 | 超 300 / 200 → **直接失败 + 告警，绝不静默截断** | `REPLACE` 全量 + 截断 = **静默删除被截断项**（官方警告的副作用）；"不可能事件"，触发即转人工（§9 QV2-17） |

| ★ **`action_context`（推送纪律）** | **每次推实例，每个 `RELEASED` 任务的 `task_list[].action_context` 必须写含 `biz_no` 的 JSON**：`{"biz_no":"…","task_id":"…"}`；★ **`action_configs` 须配「同意 / 拒绝」两键** | ★ **官方回调【不发】顶层 `biz_no`，本字段是 `biz_no` 回传的【唯一载体】**；不设 ⇒ 回调取不到 `biz_no`、**恒 400**（`04a §3.2`；第 2 批 `d94580f`） |

|---|---|---|
| 事实 | 快捷回调 `action_callback_url` 是**飞书 → 我方**的**入站**请求 | ★ 与 `04 §0`「无入站端口、无公网 IP」**直接冲突** → 须在 `04 §0` **显式单点解除**并声明（**QV2-A19**） |
| ★★ **前提纠正（V1.4）** | **不存在"既有对外 HTTPS 面"可复用**：`.env.example` 为 `JX_LISTEN_ADDR=127.0.0.1:8080`（**仅本机回环**）、**仓库内无任何反向代理 / TLS 配置**；且用户"随时可以部署"＝**尚未部署** → **原"复用既有对外 HTTPS 面"的前提不成立** | 因此 §6.4 由"最小偏离"改为「**从零规划对外 HTTPS 面**」；这是 D1 对本文的实质修正 ★ **（★ 已于 V1.16 修正表述：HTTPS 属我方选择、非平台要求，见 `04a §17.0`）** |
| 要求 | 系统**必须暴露一个公网可达的入站端点**（★ **HTTPS 属我方选择、非平台要求**，见 `04a §17.0`）：**公网域名 + 反向代理**（**若采用 HTTPS 再加 TLS**），且**只暴露回调一条路径**（`POST /approval/external/callback`） | 无此端点 → 收不到同意/拒绝 → **口径 2 / 3 不成立** |
| 组成（从零） | ① **公网域名**（★ **具体域名待用户部署前提供 → 列入 §9**）；② **反向代理**（Nginx / Caddy 等，**终止 TLS**）；③ **TLS 证书**（见下格）；④ **加固**（仅暴露回调路径、`token` 校验、路径限速、body 上限） | D1 定案落地；**"从零"而非"复用"** |
| ★ TLS 证书方案 | ★ **建议 Let's Encrypt 自动签发 / 自动续期**（**免费、自动、无需用户提供证书**） | ★ **代价**：需 **80 / 443 对外可达**以完成 **ACME 验证**；**自动续期失败必须监控告警**（否则证书到期＝回调**全失败且静默**） |
| 安全 | 校验 `action_callback_token`（定义时下发）；`encrypt` 加密体按约定解密；非法 → **拒绝并告警**；建议 IP 白名单 | 入站面是新增攻击面，必须最小化 |
| 中间件 | 回调路径走现有 Echo 链，但**绕开会话 / OIDC 中间件**（飞书请求不带 cookie），只挂**回调专属中间件**：`token` / 签名校验 → **落盘（`t_flow_op_log`）→ 立即 200 → 入队**（第三轮 D2） | 避免"飞书请求被登录中间件拦成 401"（会表现为回调**全失败**且不知原因） |
| 防护 | 反代侧**仅放行飞书出口 IP 段**（可得则放）+ **路径级限速** + **body 上限（如 64KB）**；TLS 终结在反代 | 入站面最小化 |
| 观测 | 回调的 4xx/5xx、P99 耗时、**非法 token 计数**、★ **证书到期时间**单独打点并告警 | 呼应 `04a §10` 静默防护 S5（★ **非 `08 §4.9` 的改造位点 `S5`**，消歧见 §6.1 注） |
| 待确认 | ★ **具体公网域名**（部署前由用户提供）；是否需 WAF | QV2-A19（原"是否复用既有面"问题**已随前提纠正而消解**） |

> **一句话版本（V1.4 修订）**：**从零建立对外入站面（公网域名 + 反向代理；★ HTTPS 为我方选择，若采用则加 Let's Encrypt TLS），仅暴露一条经 `token` + IP 白名单校验的回调路径；攻击面压到最小**（不再是"复用既有一面"）。

## 7. 通讯录同步的新定位（口径 1）与转向后的可用性口径

> **机制保留**（`08` 全部：启动全量 + 事件增量 + 每周对账 + 软删只增不减 + 镜像双 ID，权威＝`open_department_id`）；**目的重写**为「**保证提交审批时部门 / 人员信息正确**」（口径 1）。

### 7.1 提交页如何用镜像信息防错

| 环节 | 防错动作 | 不一致时 | 申请人可否改 |
|---|---|---|---|
| 申请人身份 | 飞书免登拿到 `open_id` → 镜像查在职状态 / 部门 / 主管领导 | 镜像中**不存在或已停用** → **阻断**并提示"请联系管理员在飞书通讯录确认" | 不可改 |
| 部门 | **默认带出**镜像中的部门（作为 `t_instance.department` 快照），并 ★ **提交时实时回源校验一次**（D6） | ★ **提交时实时回源比对**（见下"实时比对"行）；**不一致以实时值为准 + 落不一致标记**；申请人若已知部门变更，**可手动改但必填理由 + 留痕** | **可改**（留痕） |
| 审批人（主管领导 / 总经理） | 由**分档 + 部门**自动计算（镜像），申请人**不可手选** | 计算不到（如部门无主管）→ **阻断**，提示按流程找人 | 不可改 |
| 采购经办人 / 验收人 | 审批过程中由审批人指定（`01-PRD` §4.1），**选择器只列镜像内在职、未停用人员** | 选中人已离职（推送前校验）→ 提示换人 | 不可选离职 |
| 抄送人 | 由规则带出（如综合运营主管），来源同上 | 同上 | 不可手选 |

| 设计点 | 结论 | 理由 / 代价 |
|---|---|---|
| 权威来源 | **提交时刻**：镜像快照为**基线**（默认带出），并 ★ **实时回源飞书校验一次**（D6 定案） | 口径 1"避免提交时信息错误"的直接落点 |
| ★★ 实时比对（D6 定案，**推翻 V1.1 的 C3"不做"**） | **做**：**提交时实时回源飞书一次**，校验申请人当前**部门 / 在职**信息 | 用户第三轮答复「**实时回源校验**」明文；★ **原以"P95<500ms"否掉它，现接受多一次跨网调用** |
| ★ 实时回源的超时 / 失败策略 | ★ **告警放行 + 落"不一致"标记**，**不阻断提交** | 飞书抖动 / 超时**不应让员工提不了单**；失败必须可见（告警 + 标记） |
| ★ 不一致时以谁为准 | ★ **以实时值为准**（回源得到的部门 / 在职**覆盖**镜像快照），（可选）提示申请人 | 回源值是"当下真相"；口径 1 的落点 |
| ★ 提交页响应时间 | ★ **重估**：因**多一次跨网调用**，**不再**以"P95<500ms"为硬指标 | 原 P95<500ms 是**无回源**时的目标；现按"含一次回源"重定，**具体值联调期实测** |
| ★ 调用量 | 提交时 **+1 次/单（≈ +100 次/月）** → 并入 **§5.5** 预算 | 量级不变（§5.5 已列 ~150 含四操作补推） |
| "尽可能同步"的边界 | ★ **D6 定案后**：**提交时实时回源**（对"提交时点"强校验一次）＋ **事件增量 + 每周对账**（对"日常变更"收敛）；两端合起来满足口径 1 的"尽可能" | 原"接受滞后、非实时强一致"口径**已被 D6 收窄**——提交时点改为实时校验 |
| 快照 vs 现状 | `t_instance.department` 存**提交时快照**，与飞书后续调整**允许不一致**（快照可追溯） | 与 M4 一致；行级权限依据该快照 |
| 镜像 ≠ 权限（`08` §4.10） | **增强**为「镜像 = **提交期权威** + **权限期结构性约束**」：提交期用镜像带值/校验；权限期仍按 `01-PRD` §4.2 令牌 | 避免把"镜像里有"误读成"有权限" |

### 7.2 ★ 回调处理模型与可用性口径（★ 第三轮 D2 定案）

> 用户原文（D2）：「**回调过来后，先落盘，只要落盘成功就返回 200，然后慢慢跑业务，只要落盘，不存在超时问题这就够了。**」＋「**服务挂了就挂了，那是高可用要解决的问题，不是服务本身开发要解决的问题。**」

**① 回调处理模型（D2 定案）**

| 步 | 动作 | 时延 |
|---|---|---|
| 1 | 校验（`token` / 解密 / 取 `action_context`） | — |
| 2 | ★ **落盘**：写 `t_flow_op_log` | — |
| 3 | **入队（异步）** | — |
| 4 | ★ **立即返回 HTTP 200** | **毫秒级** |

> ★ **"落盘即 200、业务异步执行"**：落盘是毫秒级 → **官方 10s 超时绰绰有余**。★ **撤销**原「按最严 5s 设计」的措辞（那是"同步跑完业务"才需要的保守值）。业务（状态机推进 / 出方向重推）在队列里慢慢跑。

**② 可用性口径（D2 定案；原 G1 反转仍在，但"降级流程"改为下述）**

| 故障场景 | 表现 | 归属 / 处置 |
|---|---|---|
| ★★ **服务整体不可用（进程不在）** | 回调**进不来、连落盘都没有** → 该次点击**"未生效"**（飞书卡片会报错 / 不更新）→ 审批人**需重新点击** | ★★ **归"高可用"，不在本系统开发范围**（用户明示："那是高可用要解决的问题"）；**不做"线下签批兜底"** |
| 飞书侧故障 | 我方流转正常，仅无法展示 / 待办 / 通知 | 推送进死信 + 退避重试；恢复后重推（★ **遵 §6.1「重推纪律」**） |
| 回调重复 / 乱序 | 幂等键 `(biz_no, task_id, op_type, round)`（4 列） + 状态机 no-op 吸收 | **不产生第二次状态迁移**；异常计数进告警（§8 FR-M0-15） |

> ★★ **撤销项（D2 定案）**：原"我方停机 → 线下 / 纸质审批应急 + 恢复后人工补录（作数口径）"**整段撤销**（用户："服务挂了就挂了，是高可用问题"）。连带 **QV2-A20 关闭**——"线下补录是否具同等审批效力"**不再存在**。

**③ ★★ 三条查实事实（一级来源，直接影响"重推"正确性）**

| # | 事实 | 影响 |
|---|---|---|
| 1 | `GET /approval/v4/external_tasks`（获三方任务状态）**只返回粗粒度 `status` + `update_time`，无操作人、无审批意见、无操作明细** | **不能**靠它还原"谁在飞书点了什么" |
| 2 | `POST /approval/v4/external_instances/check`（校验实例）**只返回 `diff_instances`**（告知需重推），**不给飞书侧操作内容** | 对账只能"发现差异 + 重推"，**拿不到操作明细** |
| 3 ★★★ | **`update_mode=REPLACE` 不校验 `update_time`，且"不包含在本次请求的数据（实例 / 任务 / 抄送 / 节点）会被清空、替换为本次数据"** | ★ **若用"落后快照"（task 仍 `PENDING`）以 `REPLACE` 重推，会把飞书侧已 `APPROVED` 的 task 覆盖回 `PENDING` ＝ 审批状态倒退、审批人的操作被静默抹掉** |
| 4 ★ 来源纠正 | 「重试 4 次（15s / 5min / 1h / 6h）」是**事件订阅**的策略，**不适用审批快捷回调**；官方对快捷回调**只写 10s 超时、未写重试** | 原文引用需更正；★ **回调不可当"永久会重试"的真相输入** |

> **处置口径（★ 重推纪律，与 §6.1 同源）**：**恢复后 / 任何重推，禁止用 `REPLACE` 推落后快照**；改用 **`UPDATE` + `update_time` 严格递增**（官方 `UPDATE` 语义＝**仅当 `update_time` 变大才更新** → **天然拒绝落后覆盖**）；或对"我方无本地变更"的实例**不覆盖**。→ 新增待实测 **QV2-A28**（§9）。

**④ 小结**

| 项 | 结论 | 理由 / 说明 |
|---|---|---|
| 对外 SLA 定位 | 我方系统＝**审批链路的必需节点** → 可用性目标须重定（原 G1 作废，待在 §10.1 与 04 重写） | 转向**最大的副作用** |
| 服务整体不可用 | ★ **归"高可用"**（用户明示）；本系统只保证"**落盘即 200、业务异步**" | **不再**承诺"线下兜底 / 补录作数"（已撤销） |
| 停机期"点了没反应" | ★ 仍**必须可见**：健康检查 / 告警（"能做的做"） | 静默失败是本仓库头号红线 |
